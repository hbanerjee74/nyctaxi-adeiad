# Ossie ontology convention — implementation plan

**Goal:** make the business ontology a first-class canonical artifact with a generic authoring skill, a validation gate and an onboarding step, proven by the five concepts VD-7282 names.

**Architecture:** vendor the pinned ontology and mapping schemas beside the core schema, teach the existing canonical-model tool to validate ontology and mapping documents, author `ontology/` for this repo, then write the generic `ontology` skill and extend `validating-semantic-model`. The domain repo is the reference implementation of a skill that ships to every customer repo.

**Spec:** [`docs/requirement/vd-7282.md`](../requirement/vd-7282.md). Decision and design: `accelerate-data/studio` `docs/adr/0220-ossie-canonical-artifacts-are-the-semantic-source-of-truth.md` and `docs/design/data-platform/ossie-canonical-artifacts.md` — product artifacts, not this repo's.

## Global constraints

- Apache Ossie `0.2.0.dev0`, upstream commit `c5cb931d72029dc523a5dd18d267f083403786f2`. Never edit a vendored file.
- Skill text is generic: artifact locations resolve from `repo-map.json`; no repo path, layer name or domain term inside a skill.
- Skill authoring and edits follow the `writing-skills` skill: a baseline run without the change, the edit, then the same scenario re-run. No skill text before the baseline is recorded.
- Mappings are declaration-only: no `requires`, no `derived_by`, no `custom_extensions`, no `prefixes`, no `iri`.
- No change to dbt models, seeds, macros or tests.
- Commands: `python3 -m pytest tests/test_ossie_validate.py -q`, `python3 -m pytest tests/test_maps.py tests/test_adr_links.py -q`, `ruff check .`, `python3 .github/scripts/adr_lint.py`.

## Review focus

1. A mapping expression naming a field the model does not expose — must fail, not pass silently.
2. A re-pin where the upstream mapping schema still `$ref`s `main` — must resolve offline or fail loudly, never fetch.
3. A concept that no `CONTEXT.md` term names, or an identity term with no concept — must fail in both directions.
4. A relationship whose declared direction or multiplicity contradicts the mart SQL — a content finding the tool cannot see.
5. A canonical document with no mapping — must be reported, never read as covered.

### Task 2: Validate ontology and mapping documents, refs and glossary drift

**Files:** Modify `scripts/ossie.py`; Test `tests/test_ossie_validate.py`

**Interfaces:**
- Produces: `ossie.py validate <dir>` detects the document kind (`ontology` key → ontology, `concept_mappings` → mapping, else model) and picks the schema; `ossie.py refs <ontology-dir> <model-dir>` prints `[{severity, code, message}]` and exits 1 on error; `ossie.py glossary <ontology-dir> <context-md>` prints the same shape.

- [x] **Step 1: Write four failing tests** — a mapping whose `semantic_model_ref.name` matches no document is an error; a mapping expression `TRIPS.no_such_field` is an error; a concept with no `**Term**:` in `CONTEXT.md` is an error; an ontology with a `requires` entry emits a `declaration-only` warning.
- [x] **Step 2: Run them — four failures**
- [x] **Step 3: Implement the kind dispatch and the two commands.** `refs` resolves each ref by document `name` in the model dir, extracts `DATASET.field` from every expression, and checks the dataset and field exist in that document; a model document with no mapping is a `mapping/none` warning. `glossary` compares concept names against `**Term**:` headings case-insensitively and reports both directions. `validate` emits `declaration-only` (warning, exit 0) for any `requires` or `derived_by`, because no evaluator reads them.
- [x] **Step 4: Run the four tests — pass**
- [x] **Step 5: Commit** `feat: validate ontology documents, mapping refs and glossary drift`
