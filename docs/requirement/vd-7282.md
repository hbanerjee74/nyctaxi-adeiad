# Requirement: Map a taxi business ontology to the canonical Ossie models (VD-7282)

## Ask

The Canonical Data Model demonstrates Ossie's analytical half and nothing of its business ontology. Establish the ontology and its mappings for the five concepts the issue names — Trip, Shift, Driver, Vehicle, Zone — as a generic convention a customer repo inherits, not as a one-repo artifact: a new authoring skill, an extended validation gate, an onboarding step, and sample artifacts with a findings report that separates what works from what is declared.

The decision and the design are product artifacts, not domain ones: `accelerate-data/studio` `docs/adr/0220-ossie-canonical-artifacts-are-the-semantic-source-of-truth.md` and `docs/design/data-platform/ossie-canonical-artifacts.md`. This repo is the reference Domain that proves them.

## Scope

In scope: the ontology document and one mapping document per canonical document; the generic `ontology` authoring skill; the ontology and mapping passes added to `validating-semantic-model`; the onboarding step that writes both; the `repo-map.json` and `test-map.json` registrations; the domain glossary terms the concepts require; the findings report and its go/no-go recommendation.

Out of scope: the product decision and design (they live in `accelerate-data/studio`); executing or exporting a mapping; an ontology query engine; cross-document query blending; a converter; production reasoning infrastructure; any change to the dbt models, seeds or macros.

## Requirements

- [x] `R-01` The ontology and mapping schemas are vendored from the same upstream commit as the core schema, resolved offline by the same registry, and a parity test fails when the checker and the vendored schemas disagree — accept when the test's re-pin case fails on a changed key set and passes on the pinned files — source: studio `docs/adr/0220-ossie-canonical-artifacts-are-the-semantic-source-of-truth.md`, "One pin, one gate"
- [x] `R-02` Trip, Shift, Driver, Vehicle and Zone are declared as entity types with natural identity through `identify_by`; no surrogate and no SCD version becomes a concept — accept when `validate` reports no concept without an identifying relationship and no concept is named after a version — source: studio `docs/design/data-platform/ossie-canonical-artifacts.md`, "Partitioning" and "Standard limits"
- [x] `R-03` The relationships state the identity and join graph the model spans: Trip to Shift, Shift to Driver, Shift to Vehicle, Trip to pickup and dropoff Zone under role names, and each direction matches the foreign key the mart has — accept when every relationship's direction and multiplicity is checked against the mart SQL and the two zone roles are one concept reached twice — source: studio `docs/design/data-platform/ossie-canonical-artifacts.md`, "Artifacts"
- [x] `R-04` There is one mapping per canonical document; each `ontology_ref` and `semantic_model_ref` resolves to a document whose `name` matches, and each expression names a dataset and field the referenced model declares — accept when the mapping check reports zero unresolved refs and zero unknown `dataset.field` expressions — source: studio `docs/design/data-platform/ossie-canonical-artifacts.md`, "Gates"
- [x] `R-05` Every canonical document is either mapped or reported as unmapped with its reason — accept when the reference check accounts for all four documents — source: studio `docs/design/data-platform/ossie-canonical-artifacts.md`, "Gates"
- [x] `R-06` The ontology and mappings are declaration-only: no `requires`, no `derived_by`, no vendor payload, no `prefixes` or `iri` — accept when `validate` reports no expression field and no extension key, and the report states the declaration status — source: studio `docs/adr/0220-ossie-canonical-artifacts-are-the-semantic-source-of-truth.md`, "Ontology mappings are declarations"
- [x] `R-07` Every concept traces to a `CONTEXT.md` term and every term denoting a thing with identity has a concept; Driver, Vehicle and Shift are added as terms because this repo's glossary lacks them — accept when the drift check reports zero untraced concepts and zero unrepresented identity terms — source: studio `docs/adr/0220-ossie-canonical-artifacts-are-the-semantic-source-of-truth.md`, "The ontology is the source of truth for business identity"
- [x] `R-08` The `ontology` skill is generic: it resolves the artifact location from `repo-map.json`, names no repo path, layer or domain term, and states the declaration-only status; `validating-semantic-model` gains the ontology and mapping passes and stops assuming the Canonical Data Model covers only gold marts — accept when neither skill contains a path that is not resolved from the map and neither names a taxi term — source: studio `docs/design/data-platform/ossie-canonical-artifacts.md`, "Artifacts" and "Gates"
- [x] `R-09` Onboarding declares `ontology/` in the maps and writes the ontology from the confirmed vocabulary; mappings are written only where canonical documents exist — accept when the onboarding skill's build step and base setup name both, with the mapping deferral stated — source: studio `docs/design/data-platform/ossie-canonical-artifacts.md`, "Lifecycle"
- [x] `R-10` A findings report records the pinned versions, the repeatable command for each demonstration, the observed output, what is declaration versus executable, how cross-document identity ambiguity is handled, and a go/no-go recommendation with follow-up scope — accept when each demonstration in the report carries its command and its observed output — source: VD-7282 test notes

- [x] `R-11` The follow-up issue that carries this convention into the product, VD-7139, is rescoped to include the ontology: seeding the `ontology` skill, the ontology passes in `validating-semantic-model`, onboarding's `ontology/` step, the ontology gates in `install-ci`, and the mapping obligation in `generating-dbt-model` — accept when VD-7139's description names each of those and no longer excludes the ontology — source: VD-7139, this requirement's R-08 and R-09

## Business decisions

| Decision | Value | Source |
| --- | --- | --- |
| Where the ontology lives in the lifecycle | The language layer, written from the glossary at onboarding | `accelerate-data/studio` `docs/adr/0220-...` |
| Whether mappings execute | They do not; they are declarations until upstream ships a parser | `accelerate-data/studio` `docs/adr/0220-...` |
| SCD versions | Not concepts; a gap recorded on the mapping | `accelerate-data/studio` `docs/adr/0220-...` |
| One ontology or one per document | One ontology, one mapping per canonical document | `accelerate-data/studio` `docs/adr/0220-...` |

## Out of scope

- Any query engine, converter or exporter that reads a mapping.
- A `ZoneVersion`, `DriverVersion` or `VehicleVersion` concept.
- Metrics in the ontology; the semantic model owns them.
- An external vocabulary link (`iri`, `prefixes`).

## Open questions

None. The spike's go/no-go recommendation answers whether the convention stays.
